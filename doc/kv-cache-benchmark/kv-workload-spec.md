# KV-cache storage-tier workload spec (v1)

Purpose: compare node-local storage backends in the role of an LLM KV-cache /
prefix-cache offload tier. Every harness implements EXACTLY this so numbers are
comparable. Output is JSON lines (one object per measurement) plus a Markdown
table printed at the end.

## Data model

- Key: 32-byte digest = SHA-256 of the ASCII string `prefix-<i>` (i = 0..N-1).
  Harnesses that need a string key use the 64-char lowercase hex of the digest.
- Value: `block_size` bytes of pseudorandom, incompressible data generated by a
  seeded xorshift64* (seed = i), so any harness can regenerate and verify block i.
- Metadata: a 64-byte header (bytes 0..63 = the digest twice). Stores with a
  separate header slot (Cyclone `set_header`) use it; others prefix it to the
  value. Report which.

## Sizes and dataset

- Block sizes (bytes): 524288 (512 KiB), 2097152 (2 MiB), 8388608 (8 MiB),
  33554432 (32 MiB). Rationale: Llama-3-8B fp16 KV ≈ 131 KB/token → 16-token
  block ≈ 2 MiB, 256-token chunk ≈ 32 MiB; 512 KiB covers small-model/quantized.
- Dataset per size: N = min(4096, floor(4 GiB / block_size)) blocks
  (512 KiB → 4096; 2 MiB → 2048; 8 MiB → 512; 32 MiB → 128).
- Store capacity: 8 GiB per run (so the dataset fits with headroom; no eviction
  in phases 1–3).

## Phases (per block size)

1. **PUT** — single writer thread, sequential i = 0..N-1, each put fully
   durable-to-the-store's-normal-semantics (no per-put fsync unless the store
   always does it; say which). Report: puts/s, GB/s, p50/p99/p99.9 µs.
2. **GET first-touch** — single thread, i = 0..N-1 in order, immediately after
   PUT (page cache warm from the write). Each get must **touch every 4 KiB page**
   of the value (sum one byte per page into a volatile sink) so lazy/zero-copy
   stores actually fault the data in. Report gets/s, GB/s, p50/p99.
3. **GET warm, Zipf** — keys drawn from Zipf(θ = 0.99) over 0..N-1 (use the
   standard "Gray et al." generator, seed 42 + thread id), threads T ∈ {1, 4, 8},
   10 s per point after a 2 s warm-up. Two access modes, run both:
   - `view`: get + touch every 4 KiB page (as in phase 2).
   - `copy`: get + memcpy the whole value into a preallocated per-thread
     buffer (simulates staging to a device transfer buffer).
   Report per (T, mode): gets/s, GB/s, p50/p99 µs.
4. **RESTART** — close the store cleanly, reopen, GET all N keys once (view
   mode, single thread). Report: hit fraction (0..1) and gets/s. A store whose
   index is not persistent reports hit fraction 0 — that is a result, not an
   error.
5. **MULTI-PROCESS READ** (optional, only if the store supports concurrent
   readers from separate processes without a server): fork P = 4 reader
   processes after PUT, each running phase-3 `view` at T = 1 for 10 s.
   Report aggregate gets/s and GB/s. Skip with a note if unsupported.

## Rules

- Release builds, `-O2` or better, same machine, same volume/directory on the
  internal SSD, nothing else running. Run each block size in a fresh store.
- Latency is measured around the get/put call PLUS the touch/copy work.
- Print machine info once: CPU model, core counts, OS version, filesystem,
  store version/commit.
- JSON line schema:
  `{"store":"cyclone","block_size":2097152,"n":2048,"phase":"get_warm","mode":"view","threads":4,"ops_per_s":..,"gb_per_s":..,"p50_us":..,"p99_us":..,"p999_us":..,"hit_fraction":..}`
  (fields not applicable are omitted).
- Store-specific tuning is allowed but must be printed and justified in the
  report (e.g. Cyclone: `max_object_size = 0`, `stripe_size` > largest block,
  `ram_cache_size = 0`, mmap directory on for phase 4/5; LMDB: `MDB_NORDAHEAD`
  off, map size 16 GiB; RocksDB: BlobDB on, block cache 0).
